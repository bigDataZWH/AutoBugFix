根因要素分解

直接原因

Redis 连接池 maxActive=8 无法支撑锁等待线程堆积，连接获取阻塞 >3s。

根本原因

分布式锁粒度按 SKU 全局加锁，未按 userId+skuId 分段，高并发下成为瓶颈。

触发条件

QPS > 800 + 大促秒杀场景，库存热点 SKU 集中访问。

衍生问题

重试未做幂等，超时后重试导致库存重复扣减，数据不一致。

结合业界开源实践与华为内部技术规范，推荐以下最佳实践。

01

分布式锁分段（Striped Lock）

将单一粗粒度锁拆分为 N 个分段锁（如 hash(skuId) % 64），锁竞争分散，QPS 承载提升 10-20 倍。参考 Java Striped<Lock> 与 Redis Redlock 分段实现。

src: Java Concurrency in Practice §13 / Redis 官方文档
02

连接池容量公式

maxActive = (峰值 QPS × 平均 RT(s)) × 1.3 冗余系数。本次场景：800 × 0.05 × 1.3 ≈ 52，建议取 64。

src: HikariCP Pool Sizing Wiki
03

幂等性三件套

前端 requestId + 服务端 SETNX 去重 + 数据库唯一索引，三层防护保证最终一致。

src: 阿里《微服务设计模式》/ 华为分布式规范 DOC-2024-117
04

熔断器自适应配置

基于实时 QPS 与 RT 动态调整熔断阈值，避免静态配置导致误熔断。推荐 Sentinel 流控规则。

src: Sentinel 官方文档 / Netflix Hystrix Wiki
05

压测基线 + 容量规划

上线前以 1.5 倍预期峰值压测，建立 p99/错误率/资源水位基线，作为熔断与扩容依据。

src: 华为性能测试规范 PERF-2023-08
