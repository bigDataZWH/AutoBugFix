01

设计目标与原则

// Design Goals & Principles

实现一个 Agent，能够自动完成问题单的 根因定位 → 方案生成 → 代码修复 → 验证 全流程，最终产出可审核的 PR。方案 C 遵循以下七条原则：

P01

自研聚焦壁垒

根因定位与验证护栏是差异化核心，必须自研并深度优化。

P02

复用成熟基建

代码修改、LSP、Git 快照等已被大规模验证的基建，复用 OpenCode。

P03

抽象层解耦

FixExecutor 接口隔离编排与执行，保留切换 / 并跑执行器的自由度。

P04

证据驱动

每个定位结论、每个补丁必须有可追溯证据，禁臆测。

P05

三重护栏

编译门 + 测试门 + 静态门，硬阻断幻觉修复。

P06

状态机驱动

每阶段准出条件明确，失败回退而非一路到底。

P07

Human-in-the-Loop

高风险变更强制人工审核。

02

为什么是方案 C

// Why Hybrid · Brain + Hands

核心洞察

问题单修复的差异化在"定位准不准、验证严不严"，不在"改代码稳不稳"

把 OpenCode 不擅长的（定位 / 验证）自研做到极致；把 OpenCode 擅长的（改代码 / LSP / Git）直接复用。

自研定位 + 验证 · 大脑 + OpenCode 改代码 · 手脚 + FixExecutor + 三重门 · 护栏

三条业界洞察支撑选型

  • Agent Harness 定律：Agent 性能中 98.4% 取决于基础设施（工具 / 沙箱 / 上下文 / 循环控制），仅 1.6% 来自 LLM 本身。→ 把工程基建做厚，不重复造轮子。
  • 定位是瓶颈：SWE-bench 失败 case 中 定位错误占 60%+。错误文件 → 错误补丁。→ 根因定位是整个系统的差异化核心。
  • 护栏比自由度更重要：三重护栏（检索脚手架 + 编译门 + 测试门）能将幻觉修复率从 ~40% 降到 <10%。→ 约束 LLM 行动空间，强制证据闭环。

三方案分维度对比

维度A · 重新自研B · 直接用 OpenCodeC · 混合（采纳）
上线速度慢（月级）快（周级）较快（2-4 周）
根因定位精度可极致优化弱（通用检索）强（自研定位）
验证护栏强度三重门可控弱（无内置）三重门可控
改代码基建成熟度需自建踩坑已验证 16M 月活复用 OpenCode
可控性 / 定制深度完全可控黑盒编排可控
可审计 / 可观测全链路 trace弱强
开发成本极高低中
外部依赖风险无高（版本 / 配额）中（可对冲）
结论 方案 A 把成熟基建也自研了，边际收益极低、风险极高；方案 B 把差异化能力也交给 OpenCode，质量上限被锁死。方案 C 把差异化能力自研做到极致、基础设施直接复用 OpenCode，并用 FixExecutor 抽象层保证"复用但不锁定"。
03

整体架构

// Architecture · 三层一抽象

输入

核心动作

定位结论（文件:函数:行号）+ 推理依据 + 置信度
交互点

输入
FixRequest

输入

核心动作

输出

交互点

S8

审核交付

输入

核心动作
生成 PR（含根因说明、修复思路、测试证据、风险标注）→ 风险分级（低 / 中 / 高）→ 路由审核

交互点
低风险自动提交待合并；中高风险强制人工审核；提供一键回滚与知识沉淀。
状态机驱动 端到端状态机：RECEIVED → UNDERSTOOD → REPRODUCED → LOCALIZED → PATCHED → VERIFIED → NEEDS_REVIEW → MERGED。任一阶段失败回退而非一路到底，迭代超过 K=3 轮自动转 NEEDS_REVIEW 人工兜底。
05

交互设计

// Interaction Design · 人机协作 · 全程可观测

长任务异步化 + 关键节点人在回路 + 全程可观测 + 一键回滚。先明确"哪些自动、哪些需确认、哪些必须人工"，避免黑盒与失控。

人机协作边界

协作模式适用阶段人工参与典型场景
全自动S1 / S3 / S6 / S7无链接拉取、索引构建、补丁生成、跑门验证
半自动确认S2 / S4关键节点确认类型歧义澄清、低置信度定位确认
人工审核S5 / S8审核后放行高风险方案、配置 / 安全变更、PR 合并
人工兜底S4 / S7失败接手定位反复失败、验证超 K 轮
禁止自动全局不可绕过删测试、改密钥、绕过门、命中禁用 diff 模式

关键交互触点

触点触发时机用户动作系统响应
链接输入启动粘贴问题单链接校验 → 拉取详情 → 进入运行态
定位确认S4 置信度不足选择 / 修正 Top-N 候选锁定定位 → 进入 S5
方案确认S5 高风险确认 / 修改修复假设下发 FixRequest → S6
补丁审核S6 完成后查看 diff 预览审计通过 → S7
验证失败S7 门失败查看证据 / 选择迭代或中止反馈迭代或回滚
完成交付S8审核 PR / 合并沉淀知识库 / 关闭工单

界面状态设计

输入态

问题单链接输入框 + 历史记录 + 示例链接；空状态引导粘贴链接即开始。

运行态

实时进度时间线（8 阶段高亮当前位置）+ 当前子任务 + 耗时 / 迭代轮次。

定位确认态

Top-N 候选列表（文件:函数:行号 + 置信度 + 证据预览）+ 选择 / 修正操作。

补丁审核态

diff 预览（文件树 + 语法高亮 +/-）+ 变更统计 + 通过 / 拒绝 / 回滚。

完成态

PR 卡片（标题 / 链接 / 风险标签）+ 根因与修复摘要 + 合并按钮。

失败兜底态

失败阶段定位 + 失败证据 trace + 重试 / 转人工 / 中止选项。

异步通知 所有长任务（定位 / 补丁 / 验证）异步执行，状态变更与关键节点（需确认 / 失败 / 完成）通过 IM / 邮件推送，用户可离开页面、收到通知后回来接手。全程保留可观测 trace 与 Git 快照，支持任意节点回滚。

核心模块设计

// Core Modules

问题理解与分类

把自然语言问题单结构化为 IssueProfile，输出可被下游消费的 schema。

分类树

Bug（逻辑 / 并发 / 资源泄漏 / 边界 / 兼容）/ Feature / 配置 / 文档 / 性能

信号提取器

从描述 / 日志 / 堆栈抽取 stack frame、error code、版本号、环境、触发条件

严重度评估

影响面（crash / data loss / security）× 复现频率

复现可行性

决定走"自动复现"还是"假设驱动"

IssueProfile · 输出字段

字段类型说明
issue_idstring问题单唯一标识
type / subtypeenum分类树，如 bug / concurrency
severityP0–P3严重度评级
signalsobject堆栈帧、错误码、关键词
reproduciblebool是否可自动复现
repro_hintsstring复现条件提示
suspected_areaslist疑似区域（路径 + 理由 + 置信度）

根因定位（核心差异化）

采用 "检索 + 导航 + 证据"三层定位，对标 Agentless + AutoCodeRover 最佳实践。

层级定位目标技术手段
第一层文件级（Where）向量检索（bge-m3）+ BM25 精确匹配 + RRF 融合 + Git 历史信号
第二层符号级（What）Tree-sitter 增量解析 AST + LSP go-to-def / find-refs + 调用图 DFS
第三层行级（Which line）LLM 结合上下文给精确行号 + 证据引用 + 置信度
证据闭环护栏 每个定位结论必须附带（代码引用、推理依据、置信度），无证据标记 LOW_CONFIDENCE。结论必须可被 LSP / AST 验证（行号存在、符号确实在该文件）。置信度 < 阈值 → 触发第二轮扩展检索或转人工。

方案编排

基于定位证据组装修复指令与约束，交付 FixExecutor。修复假设先行，再写代码。

PatchPolicy · 补丁策略约束

约束项取值作用
max_files5单次补丁最多改动文件数
max_changed_lines300变更行数上限，防大范围重写
allow_dependency_changefalse禁止改依赖锁文件
allow_test_deletionfalse禁止删测试
allow_config_changereview_only配置改动仅审核、不自动合
file_whitelist定位文件集diff 只允许落在定位指向的文件
forbidden_diff_patterns禁用模式命中即硬阻断（skip / || true / except:pass 等）
07

FixExecutor 执行抽象层

// Abstraction Layer · 复用但不锁定

隔离编排层与执行层。编排层只依赖 FixExecutor 接口，不感知底层是 OpenCode 还是自研执行器。这样执行层可切换、可并跑，迁移成本被控制在接口层内。

接口契约

编排层与执行层之间仅通过 FixRequest / FixResult 两个数据结构与四个方法通信，执行层具体实现（OpenCode 或自研执行器）对编排层不可见。

FixRequest · 执行入参

字段含义来源阶段
issue_profile问题单结构化画像S2 问题理解
localization分层定位证据（文件/符号/行）S4 根因定位
fix_hypothesis修复假设与思路S5 修复方案
patch_policy补丁约束策略S5 修复方案
repo_path仓库本地检出路径S3 代码对接
session_id会话标识，迭代时复用实例S6 补丁执行
feedback上轮失败反馈，用于迭代修正S7 验证护栏

FixResult · 执行产物

字段含义下游消费者
success本次执行是否成功产出补丁编排层流转判定
session_id回传会话标识，供迭代复用S6 迭代
diff统一 diff 文本DiffAuditor / 审核人
changed_files变更文件清单DiffAuditor 越界检查
tool_calls工具调用轨迹（可观测）审核 / 追溯
snapshot_refGit 快照引用，用于回滚S7 失败回退
executor_log执行器内部日志可观测 / 排障
error失败原因（成功时为空）反馈迭代

FixExecutor · 四个方法

方法职责触发时机
execute首次生成补丁，返回 FixResultS5 方案确认后
iterate携带失败 feedback 再次修正S7 验证不通过
rollback按快照引用回退仓库状态验证失败 / 用户取消
health_check探活执行后端是否就绪每次调用前 + 启动自检

DiffAuditor · 执行后独立审计

在 FixExecutor 返回后、验证护栏前，对 diff 做独立审计。审计失败 → 直接拒绝，不进入验证阶段，反馈给 FixExecutor 迭代。审计按以下规则逐条检查，任一命中即记为违规：

审计规则检查逻辑违规即拒原因
禁用模式扫描逐条比对 PatchPolicy.forbidden_diff_patterns 是否出现在 diff 中疑似绕过验证（skip / 注释断言 / except:pass）
文件白名单校验解析 diff 涉及的变更文件，逐一核对是否在 file_whitelist 内越界修改了定位证据之外的文件
文件数上限变更文件数与 PatchPolicy.max_files 比较改动范围失控，违反最小变更原则

审计产出 AuditReport（passed 布尔 + violations 清单）。passed=false 时编排层跳过验证阶段，直接带着 violations 进入 iterate 回路。

OpenCode 集成实现

// Integration · 三通道 + 自定义 Agent

OpenCode 能力映射

原需自研模块OpenCode 能力复用方式
LSP 语义导航内置 LSP（20+ 语言，实时诊断反馈）启用 OPENCODE_EXPERIMENTAL_LSP_TOOL
补丁生成Build Agent（文件读写、跨文件编辑）opencode run --agent issue-fixer
终端 / 沙箱内置终端工具编排层验证阶段调用
Git 集成Git 快照 + /undo /redo利用回滚做验证失败回退
多候选多会话并行并行 opencode run

三种集成通道

通道 1

opencode run

单次调用，补丁生成阶段。冷启动，--format json 返回结构化结果。

通道 2

opencode serve

常驻后端，多轮迭代修复。--attach + --session 复用实例，消除冷启动。

通道 3

MCP Server 桥接

自研代码智能层反向注入，让 Build Agent 主动检索定位证据。

三通道调用时序

三条通道并非互斥，而是按阶段组合：补丁生成走通道 1 冷启动一次产出，验证失败迭代走通道 2 复用会话消除冷启动，通道 3 始终为 Build Agent 提供反查能力。各通道的调用模式如下：

通道调用模式输入输出会话管理
通道 1 · run单次子进程调用修复指令 + 定位证据 + PatchPolicy结构化 JSON（diff / changed_files）一次性，无状态
通道 2 · serve常驻后端 + 多轮 attach上轮失败反馈（测试输出 / diff 审计结果）结构化 JSON（修正后 diff）session_id 复用实例
通道 3 · MCP注册自研代码智能 ServerBuild Agent 主动发起的检索请求定位证据 / 依赖图 / 调用链由编排层注入，常驻

OpenCodeExecutor · 默认实现职责

OpenCodeExecutor 是 FixExecutor 的默认实现，负责把编排层的语义请求翻译成 OpenCode 的通道调用，并把 OpenCode 的结构化输出回填为 FixResult。其内部职责拆解如下：

内部职责做的事对接通道
后端探活探测常驻 serve 是否就绪，未就绪则拉起通道 2
提示构造把 FixRequest（画像/定位证据/假设/约束）拼装为修复指令—
调用编排按 attach + session + agent + format 组装调用，设定超时通道 1 / 2
会话复用首次建会话，迭代时带 session_id 复用同一实例通道 2
结果解析解析 OpenCode JSON 输出，回填 diff / changed_files / 快照引用—
迭代与回滚iterate 携带 feedback 重跑；rollback 按快照回退工作区通道 2

问题知识库

// Issue Knowledge Base · 输入增强与经验复用

核心难点 问题单初始输入往往残缺——描述含糊、无复现步骤、无日志、代码仓未关联；而历史已解决问题单中沉淀了大量"症状→根因→修复"的可复用经验。输入不完整与经验未复用是 Agent 能力的关键分水岭。本节借鉴 OM-RAG、KnowledgeForge、Lingxi、Nemotron-CORTEXA 等业界最佳实践，给出"渐进式输入获取 + 结构化知识库 + 混合检索 + 闭环运营"的完整方案。

10.1 输入渐进式获取

业界实践（JoyCode-CSR、SWE-Fixer、AutoCodeRover）表明：不依赖一次性喂入完整上下文，而是多轮主动补全 + 知识增强逐步逼近完整 IssueContext。

第 1 轮

种子输入 · 问题单原文

获取内容
标题 / 描述正文 / 附件截图 / 优先级标签 / 关联模块
抽取信号
关键词、错误码、异常类名、堆栈关键字、受影响功能模块
产物
结构化 IssueSeed（症状向量雏形）
交互
若关键字段缺失（如无复现步骤），标记为"待补全"，进入第 2 轮。
第 2 轮

主动补全 · Agent 探查

代码仓探查
基于关键词 BM25/Embedding 搜索相关文件 → 拉取 Repo Map 局部视图
日志/trace 补全
从日志平台按错误码/时间窗拉取堆栈 trace；无可复现则请求运行时采集
关联信息
向问题单系统补查关联工单、近期变更记录、同模块历史告警
交互
若仍信息不足，生成澄清问题清单回问提单人（结构化卡片，一键确认/补充），而非盲目猜测。
第 3 轮

知识增强 · 历史召回

向量召回
用当前症状向量召回 Top-K 历史相似问题
假设注入
将历史根因结论与修复路径作为候选上下文注入 issue context
产物
完整 IssueContext（症状 + 代码 + 日志 + 历史经验）
关键
第 3 轮是输入完整度的"跃迁点"——历史经验补全了当下缺失的因果链。

10.2 知识库结构化建模

OM-RAG 的核心洞察：将已解决问题索引为结构化三元组而非无结构文本块，诊断准确率达 0.931，较 chunk 检索提升 +186%。

知识字段含义来源 / 产出阶段
症状 Symptom错误现象、报错码、影响范围、复现条件问题单原文抽取 · S1–S2
根因 RootCause缺陷定位结论、责任模块、缺陷类型分类S4 根因定位产出
修复 Resolution修改文件清单、diff 摘要、验证用例、修复策略标签S6 补丁执行 + S7 验证沉淀
程序性知识可迁移的定位步骤、修复套路、易踩坑（Lingxi 层次化抽象）LLM 从历史修复中抽象提炼
Lingxi 层次化抽象 单条修复经验 → 抽象为 "问题类型 → 定位策略 → 修复模板" 的过程性知识，可跨问题复用。低频具体经验向上归并为高频通用策略，使知识库兼具具体可检索与抽象可迁移两层。

10.3 混合检索机制

Nemotron-CORTEXA 训练任务感知代码嵌入模型，召回率比 BM25 高 31.28%、比 Agentless 高 6.4%。单一通道不足，采用三通道融合。

通道 A

向量语义召回

症状 + 根因文本 embedding（bge-m3 / 自训练 code-aware 模型）→ Qdrant ANN 召回 Top-K。擅长"描述不同但本质相似"的跨表述匹配。

通道 B

图谱多跳推理

Tree-sitter AST + 缺陷三元组构建知识图谱（KuzuDB），社区检测（Leiden）聚类同模块缺陷链，图遍历定位"同一调用链历史缺陷"。擅长根因关联与跨文件传播。

通道 C

关键词精确匹配

错误码、函数名、异常类 BM25（Tantivy）精确匹配。擅长确定性信号锚定，作为前两通道的兜底与去噪基准。

融合策略 三通道结果按 RRF（Reciprocal Rank Fusion） 加权合并 → Cross-Encoder 精排 → 取 Top-K 注入上下文。向量覆盖语义相似、图谱覆盖因果关联、关键词保证精确锚定，三者互补。

10.4 知识库闭环运营

借鉴 KnowledgeForge（AWS）闭环生命周期：从已关闭问题单自动生成知识条目，经策展入库，复用反哺修复，成功修复再回写沉淀——形成越用越准的飞轮。

①
GENERATE
聚类已关闭工单 → LLM 草拟知识条目 + 根因分析
②
CURATE
分类 / 去重 / 质量评分 / 人工或 LLM 改进入库
③
REUSE
Agent 在 S2/S4/S5 召回并注入修复上下文
④
SINK
每次成功修复自动回写新三元组，飞轮闭环
质量门 入库前必须通过：根因可追溯（链接到代码 commit）、修复已验证（通过三重门）、无重复（与现有条目相似度低于阈值）。低质量条目标记降权，避免污染召回。

10.5 与业务流的集成点

业务流阶段知识库动作收益
S1 问题单接入种子输入抽取关键词 → 建立症状向量雏形为召回预热
S2 问题理解召回 Top-K 相似历史问题 → 生成根因假设候选缩短理解路径
S4 根因定位图谱召回同模块历史缺陷链 → 缩小定位范围提升定位准确率
S5 修复方案召回可迁移修复模板（程序性知识）→ 生成方案方案有据可依
S7 验证护栏召回历史验证用例 → 补充回归测试防回归
S8 审核交付修复成功 → 回写新三元组（闭环第 ④ 步）知识库持续增值
落地节奏 Phase 1：仅向量召回 + 手动录入高质量历史问题单（冷启动种子）；Phase 2：补全图谱检索 + 自动回写闭环；Phase 3：训练任务感知 code embedding 模型 + 程序性知识抽象。与演进路线对齐，避免一次性过度建设。

验证护栏

// Triple Gates · 防幻觉最后防线

门 1

编译门

补丁必须通过 build，否则拒绝。

门 2

测试门

复现用例 FAIL→PASS + 原有测试无回归 + 覆盖率不降。

门 3

静态门

lint / typecheck + 安全扫描（semgrep / codeql）。

失败处理 失败 → 收集失败证据 → 反馈 FixExecutor.iterate()（最多 3 轮）→ 超过 3 轮转 NEEDS_REVIEW 并附带失败 trace。
