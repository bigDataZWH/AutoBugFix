01

设计目标与原则

// Design Goals & Principles

实现一个 Agent，能够自动完成问题单的 根因定位 → 方案生成 → 代码修复 → 验证 全流程，最终产出可审核的 PR。方案 C 遵循以下七条原则：

P01

自研聚焦壁垒

根因定位与验证护栏是差异化核心，必须自研并深度优化。

P02

复用成熟基建

代码修改、LSP、Git 快照等已被大规模验证的基建，复用 OpenCode。

P03

抽象层解耦

FixExecutor 接口隔离编排与执行，保留切换 / 并跑执行器的自由度。

P04

证据驱动

每个定位结论、每个补丁必须有可追溯证据，禁臆测。

P05

三重护栏

编译门 + 测试门 + 静态门，硬阻断幻觉修复。

P06

状态机驱动

每阶段准出条件明确，失败回退而非一路到底。

P07

Human-in-the-Loop

高风险变更强制人工审核。

02

为什么是方案 C

// Why Hybrid · Brain + Hands

核心洞察

问题单修复的差异化在"定位准不准、验证严不严"，不在"改代码稳不稳"

把 OpenCode 不擅长的（定位 / 验证）自研做到极致；把 OpenCode 擅长的（改代码 / LSP / Git）直接复用。

自研定位 + 验证 · 大脑 + OpenCode 改代码 · 手脚 + FixExecutor + 三重门 · 护栏

三条业界洞察支撑选型

  • Agent Harness 定律：Agent 性能中 98.4% 取决于基础设施（工具 / 沙箱 / 上下文 / 循环控制），仅 1.6% 来自 LLM 本身。→ 把工程基建做厚，不重复造轮子。
  • 定位是瓶颈：SWE-bench 失败 case 中 定位错误占 60%+。错误文件 → 错误补丁。→ 根因定位是整个系统的差异化核心。
  • 护栏比自由度更重要：三重护栏（检索脚手架 + 编译门 + 测试门）能将幻觉修复率从 ~40% 降到 <10%。→ 约束 LLM 行动空间，强制证据闭环。

三方案分维度对比

维度A · 重新自研B · 直接用 OpenCodeC · 混合（采纳）
上线速度慢（月级）快（周级）较快（2-4 周）
根因定位精度可极致优化弱（通用检索）强（自研定位）
验证护栏强度三重门可控弱（无内置）三重门可控
改代码基建成熟度需自建踩坑已验证 16M 月活复用 OpenCode
可控性 / 定制深度完全可控黑盒编排可控
可审计 / 可观测全链路 trace弱强
开发成本极高低中
外部依赖风险无高（版本 / 配额）中（可对冲）
结论 方案 A 把成熟基建也自研了，边际收益极低、风险极高；方案 B 把差异化能力也交给 OpenCode，质量上限被锁死。方案 C 把差异化能力自研做到极致、基础设施直接复用 OpenCode，并用 FixExecutor 抽象层保证"复用但不锁定"。

核心模块设计

// Core Modules

问题理解与分类

把自然语言问题单结构化为 IssueProfile，输出可被下游消费的 schema。

分类树

Bug（逻辑 / 并发 / 资源泄漏 / 边界 / 兼容）/ Feature / 配置 / 文档 / 性能

信号提取器

从描述 / 日志 / 堆栈抽取 stack frame、error code、版本号、环境、触发条件

严重度评估

影响面（crash / data loss / security）× 复现频率

复现可行性

决定走"自动复现"还是"假设驱动"

根因定位（核心差异化）

采用 "检索 + 导航 + 证据"三层定位，对标 Agentless + AutoCodeRover 最佳实践。

层级定位目标技术手段
第一层文件级（Where）向量检索（bge-m3）+ BM25 精确匹配 + RRF 融合 + Git 历史信号
第二层符号级（What）Tree-sitter 增量解析 AST + LSP go-to-def / find-refs + 调用图 DFS
第三层行级（Which line）LLM 结合上下文给精确行号 + 证据引用 + 置信度
证据闭环护栏 每个定位结论必须附带（代码引用、推理依据、置信度），无证据标记 LOW_CONFIDENCE。结论必须可被 LSP / AST 验证（行号存在、符号确实在该文件）。置信度 < 阈值 → 触发第二轮扩展检索或转人工。

方案编排

基于定位证据组装修复指令与约束，交付 FixExecutor。修复假设先行，再写代码。

PatchPolicy · 补丁策略约束json
{
  "max_files": 5,
  "max_changed_lines": 300,
  "allow_dependency_change": false,
  "allow_test_deletion": false,
  "allow_config_change": "review_only",
  "file_whitelist": ["src/main/com/app/Pool.java", "src/main/com/app/Service.java"],
  "forbidden_diff_patterns": [
    "@pytest.mark.skip", "pytest.skip(", "|| true",
    "continue-on-error: true", "except: pass", "except Exception: pass"
  ]
}
05

FixExecutor 执行抽象层

// Abstraction Layer · 复用但不锁定

隔离编排层与执行层。编排层只依赖 FixExecutor 接口，不感知底层是 OpenCode 还是自研执行器。这样执行层可切换、可并跑，迁移成本被控制在接口层内。

接口契约

fix_executor.py · Protocol 契约python
from typing import Protocol
from pydantic import BaseModel


class FixRequest(BaseModel):
    issue_profile: dict
    localization: dict
    fix_hypothesis: str
    patch_policy: dict
    repo_path: str
    session_id: str | None = None
    feedback: str | None = None


class FixResult(BaseModel):
    success: bool
    session_id: str
    diff: str
    changed_files: list[str]
    tool_calls: list[dict]
    snapshot_ref: str
    executor_log: str
    error: str | None = None


class FixExecutor(Protocol):
    def execute(self, request: FixRequest) -> FixResult: ...
    def iterate(self, request: FixRequest, feedback: str) -> FixResult: ...
    def rollback(self, session_id: str, snapshot_ref: str) -> bool: ...
    def health_check(self) -> bool: ...

DiffAuditor · 执行后独立审计

在 FixExecutor 返回后、验证护栏前，对 diff 做独立审计。审计失败 → 直接拒绝，不进入验证阶段，反馈给 FixExecutor 迭代。

diff_auditor.pypython
class DiffAuditor:
    def audit(self, diff: str, policy: PatchPolicy) -> AuditReport:
        violations = []
        for pattern in policy.forbidden_diff_patterns:
            if pattern in diff:
                violations.append(f"禁用模式命中: {pattern}")
        changed = parse_changed_files(diff)
        for f in changed:
            if f not in policy.file_whitelist:
                violations.append(f"越界修改: {f}")
        if len(changed) > policy.max_files:
            violations.append(f"文件数超限: {len(changed)} > {policy.max_files}")
        return AuditReport(passed=len(violations) == 0, violations=violations)

OpenCode 集成实现

// Integration · 三通道 + 自定义 Agent

OpenCode 能力映射

原需自研模块OpenCode 能力复用方式
LSP 语义导航内置 LSP（20+ 语言，实时诊断反馈）启用 OPENCODE_EXPERIMENTAL_LSP_TOOL
补丁生成Build Agent（文件读写、跨文件编辑）opencode run --agent issue-fixer
终端 / 沙箱内置终端工具编排层验证阶段调用
Git 集成Git 快照 + /undo /redo利用回滚做验证失败回退
多候选多会话并行并行 opencode run

三种集成通道

通道 1

opencode run

单次调用，补丁生成阶段。冷启动，--format json 返回结构化结果。

通道 2

opencode serve

常驻后端，多轮迭代修复。--attach + --session 复用实例，消除冷启动。

通道 3

MCP Server 桥接

自研代码智能层反向注入，让 Build Agent 主动检索定位证据。

三通道命令示例bash
# 通道 1：单次补丁生成
opencode run --model anthropic/claude-sonnet-4 \
  --agent issue-fixer --format json \
  "{修复指令 + 定位证据 + PatchPolicy}"

# 通道 2：常驻后端 + 多轮迭代
opencode serve --port 4096
opencode run --attach http://localhost:4096 \
  --session {session_id} --format json \
  "上轮验证失败: {test_output}. 请修正补丁。"

# 通道 3：注入自研代码智能 MCP
opencode mcp add code-intelligence \
  --command "node" --args "mcp-code-intel-server.js"

OpenCodeExecutor 实现骨架

opencode_executor.py · 默认 FixExecutor 实现python
import subprocess, json

class OpenCodeExecutor:
    def __init__(self, serve_url="http://localhost:4096", model="anthropic/claude-sonnet-4"):
        self.serve_url, self.model = serve_url, model
        self._ensure_serve()

    def _ensure_serve(self):
        if not self._probe_serve():
            subprocess.Popen(["opencode", "serve", "--port", "4096"],
                             stdout=subprocess.DEVNULL)

    def execute(self, request: FixRequest) -> FixResult:
        prompt = self._build_prompt(request)
        cmd = ["opencode", "run", "--attach", self.serve_url,
               "--model", self.model, "--agent", "issue-fixer",
               "--format", "json"]
        if request.session_id:
            cmd += ["--session", request.session_id]
        cmd += [prompt]
        proc = subprocess.run(cmd, capture_output=True, text=True,
                              cwd=request.repo_path, timeout=600)
        return self._parse(proc.stdout, request)

    def iterate(self, request, feedback): ...
    def rollback(self, session_id, snapshot_ref): ...
    def _build_prompt(self, request): ...
    def _parse(self, stdout, request) -> FixResult: ...

验证护栏

// Triple Gates · 防幻觉最后防线

门 1

编译门

补丁必须通过 build，否则拒绝。

门 2

测试门

复现用例 FAIL→PASS + 原有测试无回归 + 覆盖率不降。

门 3

静态门

lint / typecheck + 安全扫描（semgrep / codeql）。

失败处理 失败 → 收集失败证据 → 反馈 FixExecutor.iterate()（最多 3 轮）→ 超过 3 轮转 NEEDS_REVIEW 并附带失败 trace。

演进路线

// Evolution · 三阶段

PHASE 1 · 0-1 月

OpenCode 集成快速闭环

  • LangGraph 状态机骨架 + WSL2 沙箱
  • 问题理解 + 向量 / BM25 检索 + Tree-sitter AST 定位
  • OpenCodeExecutor + 自定义 issue-fixer agent
  • 编译门 + 测试门
目标：单语言（Python/TS），简单 Bug 端到端跑通
PHASE 2 · 1-3 月

执行层抽象 + 定位增强

  • 定义 FixExecutor 接口，OpenCode 为默认实现
  • DiffAuditor diff 审计 + 禁用模式检测
  • LSP 语义导航 + 调用图分析
  • 多语言（Go / Java）+ 多候选补丁
  • 静态门 + 安全扫描 + Langfuse 可观测
目标：多语言、多候选、全护栏
PHASE 3 · 3-6 月

核心资产沉淀

  • 代码智能层封装 MCP Server，反向注入 OpenCode
  • 记忆与知识库 RAG，历史相似 issue 复用
  • 修复模式自学习：成功补丁反哺知识库
  • NativeExecutor 自研执行器（可选 · 并跑 / 备份）
  • Human-in-the-Loop 审核闭环优化
目标：资产沉淀、自学习、可切换
切换保险 得益于 Phase 2 抽象层，若 OpenCode 出现输出不稳定 / 配额不足 / 定制受限，可切换或并跑自研执行器，迁移成本限于接口层。
