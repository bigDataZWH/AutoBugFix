01

Phase 1 目标与边界

// Scope · 做必要的，延后复杂的

Phase 1 的目标是打通"问题单接入 → 知识召回 → 根因定位 → 结论输出"最小闭环，并在此过程中建立可复用的问题知识库。自动补丁执行、三重验证护栏等留待 Phase 2，避免一次性铺得过宽。

维度Phase 1 在范围内延后到 Phase 2+
知识库OpenCode 辅助入库 + 查询；Markdown 文件存储；冷启动种子录入向量库、图谱检索、自训练 embedding 模型
根因定位知识引导 + 代码 trace；输出根因结论与证据自动补丁生成与执行
执行层OpenCode headless 调用入库/查询/定位三类任务FixExecutor 抽象层完整封装
验证根因结论人工确认编译/测试/静态三重门自动验证
交付根因定位报告 + 可检索知识库可合并的自动补丁 PR
设计原则 最小可用优先：用 OpenCode 的 LLM + 文件搜索能力替代独立向量库基础设施，以最低成本验证"知识库 + 根因定位"核心价值，再决定后续是否升级到向量/图谱检索。
02

整体架构

// Architecture · OpenCode 三重职责

核心思路：OpenCode 同时承担知识入库、知识查询、根因定位三项职责。LangGraph 编排层负责任务调度与状态流转；知识库以 Markdown 文件存储，OpenCode 可直接读写与搜索。

为何用 OpenCode 做知识库 OpenCode 已具备文件读写、grep 搜索、LLM 推理能力，天然适合"读知识库 → 语义匹配 → 返回相关案例"。Phase 1 无需引入独立向量库，省去 embedding 模型 + 向量数据库 + 检索服务三件套的建设与运维成本，最快验证知识复用价值。
03

问题知识库设计

// Issue Knowledge Base · OpenCode 驱动入库与查询

3.1 知识模型

借鉴 OM-RAG 结构化三元组思路，每条历史问题沉淀为症状 → 根因 → 修复三元组，外加一层可迁移的程序性知识。

知识字段含义关键字段
症状 Symptom错误现象、报错码、影响范围、复现条件title · error_code · module · repro_steps
根因 RootCause缺陷定位结论、责任模块、缺陷类型conclusion · root_files · bug_type · confidence
修复 Resolution修改文件、diff 摘要、修复策略、验证用例fix_files · fix_summary · strategy · test_case
程序性知识可迁移的定位步骤与修复套路pattern · pitfalls · transferable_steps

3.2 入库流程（OpenCode 辅助）

输入一条已修复完成的问题单（含根因与修改代码），由 OpenCode 分析抽取并写入知识库。

步骤 1

输入采集

问题单数据
标题、描述、报错日志、关联模块、优先级
修复信息
根因结论、修改文件清单、diff、验证用例、fix commit
代码上下文
代码仓路径、修复涉及文件、调用链
步骤 2

OpenCode 抽取与结构化

调用方式
编排层以入库 Prompt 调用 opencode run headless，挂载代码仓
OpenCode 动作
读问题单 → 读修复 diff → 读相关代码 → LLM 抽取三元组 + 程序性知识
产出
结构化知识条目草稿（含字段填充与置信度）
Prompt 要点
明确要求 OpenCode 输出固定 frontmatter + 分节正文，并标注 evidence（代码位置），避免凭空生成。
步骤 3

质量校验与去重

去重
OpenCode 扫描知识库现有条目，与草稿比对相似度，标记疑似重复
完整性校验
根因可追溯到 commit、修复文件非空、关键字段齐全
人工确认
Phase 1 入库需人工 review 后落盘，保证种子质量
步骤 4

落盘与索引

写入
按模块分类写入 knowledge-base/<module>/<ID>.md
索引更新
OpenCode 追加/重建 _index.md（模块、关键词、根因类型摘要）
版本管理
知识库纳入 Git，每次入库即一次可 review 的提交
入库节奏 批量冷启动：Phase 1 初期批量导入历史已修复高质量问题单（OpenCode 逐条抽取）作为种子；增量沉淀：Phase 2 补丁修复成功后自动触发入库，形成飞轮。本阶段以批量冷启动为主。

3.3 查询流程（OpenCode 辅助）

输入一条新问题单，由 OpenCode 检索知识库并返回最相关的历史案例。

查询 1

关键词锚定

输入
新问题单的症状关键词、错误码、异常类名、模块
OpenCode 动作
用 ripgrep/grep 在知识库目录中精确匹配错误码与关键词
产出
候选条目集合（精确匹配池）
查询 2

语义匹配与排序

读取候选
OpenCode 读取候选条目全文 + 索引摘要
LLM 判定
对每个候选，LLM 判定与新问题的语义相似度并打分排序
产出
Top-K 相似案例（含根因、修复策略、可迁移步骤）
关键
OpenCode 的 LLM 在此替代 embedding 模型做语义判断；当候选过多时先读 _index.md 粗筛再读全文精排，控制 token 消耗。
检索增强点 查询结果直接注入根因定位任务的上下文——历史根因作为候选假设、历史修复路径作为定位方向。这是输入完整度的"跃迁点"，补全新问题单缺失的因果链。

3.4 存储方案

选择Markdown 文件 + YAML frontmatter，因 OpenCode 可直接读写、人可 review、Git 可版本管理，零额外基础设施。

层级方案说明
主存储Markdown + frontmatter每个条目一个 .md 文件，frontmatter 存结构化字段，正文存症状/根因/修复
索引_index.md（自动生成）按模块聚合的摘要索引：ID、关键词、根因类型，供 OpenCode 粗筛
增强（可选）SQLite FTS5条目增多后补全文检索索引，入库时同步写入；Phase 1 可选
版本管理Git知识库即代码仓库，入库/修改均有可追溯提交
目录结构 knowledge-base/ 下按模块分目录（如 module-auth/、module-payment/），每模块内 <MODULE>-<NNN>.md 命名；根目录 _index.md 汇总。OpenCode 检索时先按模块缩小范围，再精确 + 语义匹配。
04

根因定位设计

// Root Cause Localization · 知识引导 + 代码 trace

4.1 输入渐进式获取

初始输入不完整是常态。采用三轮渐进逼近完整 IssueContext。

S1
ROUND 1
种子输入 · 问题单原文抽取关键词与错误码
S2
ROUND 2
主动补全 · OpenCode 探查代码仓 + 拉取日志
S3
ROUND 3
知识增强 · 召回历史相似问题注入假设
CTX
OUTPUT
完整 IssueContext 交付定位
信息不足时 若第 2 轮后仍信息不足，生成澄清问题清单回问提单人（结构化卡片，一键确认/补充），而非盲目猜测根因。

4.2 定位流水线

由 OpenCode 执行，编排层调度，分阶段产出可追溯的根因结论。

L1
LOCALIZE
缩小范围 · 锚定可疑文件/模块
L2
TRACE
代码 trace · 沿调用链追根因
L3
VERIFY
证据收集 · 代码片段佐证假设
L4
REPORT
结论输出 · 根因 + 证据 + 置信度

4.3 定位策略

策略 A

知识引导假设

优先用查询召回的历史根因作为候选假设。若新问题与历史案例高度相似，直接验证历史根因是否复现，大幅缩短定位路径。

策略 B

代码 trace 溯源

从报错点/异常栈出发，OpenCode 沿调用链回溯：grep 引用 → 读函数实现 → 定位缺陷代码。结合 Tree-sitter 符号定位提升精度。

策略 C

证据闭环验证

每个根因假设必须有代码证据支撑（具体文件 + 行 + 片段）。无证据的假设降权或丢弃，防止 LLM 幻觉。

4.4 输出规范

根因定位报告是 Phase 1 的核心交付物，结构固定、可追溯。

报告字段内容
根因结论一句话根因 + 缺陷类型分类（逻辑错误/资源泄漏/并发/配置 等）
责任位置文件路径 + 行号区间 + 责任函数/模块
代码证据佐证根因的代码片段 + 调用链 trace
参考案例知识库召回的 Top-K 相似历史问题 ID + 复用说明
置信度高/中/低 + 置信理由 + 待确认疑点
下一步建议建议修复方向（为 Phase 2 补丁生成铺路）
防幻觉 Phase 1 不自动改代码，但根因结论仍需人工确认。置信度为"低"或证据不足时，报告标注 NEEDS_REVIEW 并回问提单人补充信息。
05

OpenCode 集成

// OpenCode · 三类 Headless 任务调用

编排层通过 opencode run headless 模式调用 OpenCode，按任务类型传入不同 Prompt 与工作目录。三类任务共享同一 OpenCode 实例与代码仓挂载。

任务触发时机工作目录OpenCode 职责
入库批量冷启动 / 修复完成后代码仓（只读修复 diff）读问题单 + diff → 抽取三元组 → 写 .md → 更新索引
查询新问题接入后、定位前知识库目录grep 关键词 → 读候选 → LLM 语义排序 → 返回 Top-K
定位知识召回后代码仓 + 注入历史知识代码 trace → 证据收集 → 输出根因报告
OpenCode 能力用于说明
文件读写入库 / 查询写入知识条目、读取候选、更新索引
grep / ripgrep查询 / 定位知识库关键词匹配、代码符号搜索
LLM 推理入库 / 查询 / 定位三元组抽取、语义排序、根因推断
代码仓导航定位读函数实现、追调用链、符号定位
headless CLI全部编排层程序化调用，传入结构化 Prompt
Prompt 设计原则 三类任务各自维护结构化 Prompt 模板：明确输入字段、要求输出格式（固定 frontmatter / JSON）、强制标注 evidence、限定动作范围（入库只写知识库、定位只读不写代码），降低越界与幻觉。

交互设计

// Interaction · Phase 1 关键状态

理解中

Agent 正在抽取关键词、拉取日志、探查代码仓。

进度可见，可中途补充信息。

待澄清

信息不足，展示澄清问题卡片。

提单人一键确认或补充复现步骤。

已召回

展示 Top-K 相似历史案例。

提单人可标记相关/不相关，辅助定位。

根因已出

展示根因报告（结论+证据+置信度）。

人工确认，标记待修复进入 Phase 2。

需人工

定位置信度低或证据不足。

标注 NEEDS_REVIEW，回问补充信息。
